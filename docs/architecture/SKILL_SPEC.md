# Skill Governance Spec

这份文档定义的不是“Codex skill”，而是 `MeituanAgent` 里的**能力治理规范**。

目标很简单：

- 让系统第一次用就能尽量理解
- 让后续补强有明确收口标准
- 让规则、词典、回归、展示都能长期维护
- 避免一直靠手工微调把代码堆乱

## 1. 核心原则

1. **少量稳定能力层**
   - 核心标签尽量少而稳，不追求穷举。
2. **同义归一优先**
   - 用户说法先映射到标准标签，再进入业务流程。
3. **未知表达保留**
   - 识别不出来的内容不能丢，要进 `unclassified_clues`。
4. **规则与数据分离**
   - 词典、别名、阈值、权重、样例要分层管理。
5. **回归门禁**
   - 任何改动都要能被离线样例检查。
6. **展示给用户的解释，不能泄露内部实现细节**
   - 知识解释页是产品能力，不是调试台。

## 2. 名词定义

### 2.1 Canonical skill

系统内部统一使用的标准能力标签。

示例：

- `food`
- `coffee`
- `photo`
- `culture`
- `relaxed`
- `night_view`
- `queue`
- `rainy_day`
- `local_feature`

### 2.2 Alias

用户常说的各种表达、同义词、口语化说法、UI chip 文案。

示例：

- `吃点好的` -> `food`
- `拍照打卡` -> `photo`
- `松弛感` -> `relaxed`
- `别太商业` -> `local_feature`
- `不想排队` -> `queue`

### 2.3 Unknown

当前还不能稳定归一的表达。

处理方式：

- 保留到 `unclassified_clues`
- 不要直接丢弃
- 不要为了它马上新增 canonical skill

示例：

- `citywalk感`
- `氛围感`
- `想要一点松弛但又别太散`

### 2.4 Regression case

用于离线检查的样例，确保改词典、改 prompt、改规则后没有把旧能力改坏。

## 3. 能力分层

### 3.1 核心标签层

这一层只放少量稳定标签。

建议只保留真正会影响路线决策的能力：

- 餐饮
- 咖啡
- 拍照
- 文化
- 本地特色
- 轻松
- 夜景
- 不排队
- 雨天

这一层不追求多，追求稳定。

### 3.2 别名层

这一层负责把各种口语、同义词、UI 文案收敛成标准标签。

这一层可以持续扩，但不建议无限扩。

原则：

- 同一个意思，优先加入别名，不要新增标签
- 高频表达优先补
- 能稳定归一的表达才进词典

### 3.3 未知层

这一层负责保留系统还没把握住的表达。

要求：

- 不删除
- 不硬猜成某个标签
- 不进入主业务决策链的强约束
- 进入回归和日志，等待后续收口

### 3.4 回归层

这一层负责把系统改动控制住。

任何补词典、改 prompt、改规则、改评分，都应至少跑一次离线回归。

## 4. 什么时候加什么

### 4.1 加到 canonical skill

满足以下条件时，才考虑新增标准标签：

1. 这个需求是稳定存在的，不是偶发说法
2. 它会明显影响路线选择
3. 它不是已有标签的简单别名
4. 它可以被用户理解
5. 它能形成长期复用的产品语义

例子：

- `night_view`
- `rainy_day`
- `queue`
- `relaxed`

### 4.2 加到 alias

满足以下条件时，优先加到别名层：

1. 和现有标签语义一致
2. 只是换了个说法
3. 用户高频会说
4. 不加会影响首用体验

例子：

- `出片` -> `photo`
- `打卡` -> `photo`
- `吃点好的` -> `food`
- `别太绕` -> `relaxed`

### 4.3 保持 unknown

满足以下条件时，先别加任何标签：

1. 语义还不稳定
2. 说法太长尾
3. 有歧义
4. 还看不出是否会影响长期路线策略

例子：

- `citywalk感`
- `松弛感`
- `氛围感`

## 5. 变更流程

推荐流程如下：

1. 先在日志里收集真实表达
2. 看它是新能力、别名，还是未知表达
3. 优先补到词典或别名层
4. 更新 `eval_cases.json`
5. 跑离线回归
6. 通过后再上线

不要跳过回归直接改主逻辑。

## 7. 用户能看到什么

用户应该看到的是：

- 系统理解了什么
- 为什么这么推荐
- 哪些表达还不确定
- 如何修改路线

不应该看到的是：

- 内部词典结构
- 全量规则代码
- 调试用的字段名

所以“知识解释页”是产品功能，不是开发面板。

## 8. 泛化策略

这套系统的泛化，不靠穷举，而靠四件事：

1. **标准标签少而稳**
2. **别名层持续吸收新表达**
3. **未知表达保留到日志和回归**
4. **离线回归防止越改越乱**

如果后续场景明显变复杂，再考虑更重的编排能力，比如：

- RAG
- LangChain
- ReAct

但它们是后续增强，不是当前治理主轴。

## 9. 维护清单

每次改动前，先问自己：

1. 这是标签，还是别名？
2. 这是稳定能力，还是长尾表达？
3. 需要补词典，还是补回归？
4. 需要改规则，还是改路线策略？
5. 这次改动会不会影响首用体验？

如果这五个问题答不清楚，就不要直接往主逻辑里加 if/else。

## 10. 本项目建议的 skill 列表

如果把 `MeituanAgent` 当成一个可持续演进的产品，建议把能力拆成这些 skill：

1. `intent_parsing`
   - 把自然语言稳定归一成结构化意图。
2. `route_generation`
   - 根据意图和 POI 数据生成可执行路线。
3. `route_modification`
   - 对已有路线做二次调整，并尽量继承上下文。
4. `poi_enrichment`
   - 把 POI 数据补全、补标签、补场景信号。
5. `map_resolution`
   - 对接天地图和本地兜底能力，负责地理编码、路径规划、地图预览。
6. `route_explanation`
   - 把为什么这么选解释给用户看。
7. `knowledge_explanation`
   - 给用户看系统如何归类表达和偏好。
8. `offline_evaluation`
   - 用回归样例检查改动是否破坏已有能力。

每个 skill 都建议继续套用同一套治理标准：

- canonical tag
- alias
- unknown
- regression

## 11. 一句话总结

这套规范的目标不是“让系统什么都知道”，而是：

- 先稳定核心能力
- 再吸收用户表达
- 再保留未知
- 再用回归收口

这样后面才能持续优化，而不是越改越散。
