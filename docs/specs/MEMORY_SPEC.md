# 记忆与画像规范

这份规范只做一件事：定义路线规划系统里，记忆和用户画像怎么存、怎么读、怎么更新、怎么衰减。

目标不是把聊天记录无限堆大，而是让系统真正“越用越懂用户”，同时保持轻量、可维护、可回放。

## 1. 设计原则

- 记忆必须影响结果，不能只做展示。
- 优先存结构化信息，不存大段自由文本。
- 新信息要有证据、有时间、有权重。
- 临时偏好和长期偏好要分开。
- 多轮修改要能回放和回滚。
- 记忆要能衰减，不能永久霸占画像。

## 2. 记忆分层

### L1 工作记忆

当前一轮正在处理的内容。

建议存：
- 当前输入
- 当前澄清问题
- 当前补充答案
- 当前修改 patch
- 当前模式：generate / clarify / modify / confirm

用途：
- 让系统知道“这一轮在做什么”
- 支持单轮澄清和短链路修改

### L2 会话记忆

一次会话里最近几轮最有用的上下文。

建议存：
- 当前城市
- 当前路线
- 最近一次修改
- 最近一次澄清答案
- 最近几轮对话摘要

用途：
- 支持“再轻松一点”
- 支持“刚才那个改一下”

### L3 路线记忆

专门保存路线版本，不和普通聊天混在一起。

建议存：
- route v1 / v2 / v3
- 每次修改 patch
- 每版预算、时长、站点数、策略
- 当前选中方案和备选方案
- 路线差异

用途：
- 支持路线对比
- 支持版本回退
- 支持解释“为什么变了”

### L4 用户画像记忆

跨会话长期保存的偏好和习惯。

建议存：
- 常用城市
- 常见预算区间
- 常见节奏偏好
- 喜欢的场景
- 常见避让项
- 常用交通方式
- 常见同行人群

用途：
- 首次输入时提供默认偏好
- 长期使用时更像“懂你”

### L5 行为记忆

从用户行为里反推偏好。

建议存：
- 收藏了什么路线
- 复制了什么摘要
- 经常把路线改成什么样
- 经常选哪种方案
- 经常避开什么类型

用途：
- 行为信号通常比口头表达更真实
- 对画像更新很重要

### L6 知识记忆

系统的规则和事实层，不是用户画像本身。

建议存：
- intent lexicon
- capability registry
- policy 配置
- POI 事实
- 城市别名
- 标签映射
- 路由规则

用途：
- 让系统稳定理解用户
- 让系统知道怎么打分、怎么路由、怎么解释

## 3. 画像字段建议

### 基础画像
- `home_city`
- `frequent_cities`
- `preferred_duration`
- `preferred_budget_band`
- `preferred_transport`

### 场景画像
- `date`
- `friends`
- `family`
- `solo`
- `citywalk`
- `shopping`
- `food_first`
- `photo_first`
- `culture_first`
- `night_view`

### 风格画像
- `relaxed`
- `efficient`
- `compact`
- `quiet`
- `popular`
- `local_feature`
- `indoor_pref`
- `outdoor_pref`

### 避让画像
- `avoid_queue`
- `avoid_crowded`
- `avoid_far`
- `avoid_high_price`
- `avoid_tiring`

## 4. 写入规则

只有足够强的信号才写入长期画像。

### 建议写入的信号
- 用户明确说出偏好
- 用户连续多次修改都指向同一方向
- 用户收藏/复制某类路线
- 用户多次选择同一类方案

### 不建议写入的信号
- 单次临时情绪
- 一次性路过式表达
- 不完整的草稿输入
- 置信度很低的猜测

## 5. 读取规则

### 生成路线时读取什么
- 当前 session 偏好
- 长期画像偏好
- 最近的修改方向
- 当前城市和时间窗口

### 修改路线时读取什么
- 当前路线版本
- 最近 patch
- 当前选择的方案
- 用户明确说过的限制

### 澄清时读取什么
- 当前缺失槽位
- 当前冲突约束
- 用户历史里最常稳定的默认偏好

## 6. 冲突规则

当新旧偏好冲突时，优先级建议如下：

1. 当前 session 明确表达
2. 最近一次修改
3. 长期稳定画像
4. 历史弱信号

如果多个长期偏好冲突，保留权重更高、更新更近的那个。

## 7. 衰减规则

画像不能永久不变。

建议给每条画像记录这些字段：
- `value`
- `confidence`
- `source`
- `first_seen_at`
- `last_seen_at`
- `hit_count`
- `decay_score`

衰减建议：
- 时间越久，权重越低
- 最近连续命中，权重上升
- 长时间未出现，自动降权

## 8. 路线如何反哺画像

路线修改行为非常重要。

例如用户：
- 一开始说“想拍照”
- 后来多次改成“更轻松一点”
- 再把预算压低

这说明用户真实偏好可能是：
- `photo`
- `relaxed`
- `budget_mid` 或 `budget_low`

所以每次 route modify、clarify、favorite、copy 都应该成为画像更新信号。

## 9. 最小实现建议

如果先做轻量版本，建议至少保留这些存储对象：

- `session_context`
- `route_versions`
- `preference_profile`
- `behavior_signals`
- `knowledge_registry`

先把这五个对象做好，再逐步增强，不要一上来做成大而重的记忆黑盒。

## 10. 结论

这套记忆系统的目标是：

- 轻量，但不薄
- 结构化，但不僵硬
- 可衰减，但不丢关键偏好
- 可回放，但不靠堆长聊天记录

它应该真正服务路线生成、路线修改和用户画像，而不是只做“看起来很聪明”的展示层。
