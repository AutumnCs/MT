# 多轮对话方案

这套方案的目标不是把产品做成纯聊天，而是让用户可以用自然语言持续修改路线，同时保持整个系统可控、可维护、低 token 消耗。

## 核心原则

- 多轮对话是“状态机 + 结构化 patch”，不是自由发散的 agent 自我思考。
- LLM 负责理解、归一、补全，不负责随意改写整条路线逻辑。
- 后端负责收口、校验、记忆、回放。
- 当信息不足时，只做一轮轻量澄清，不做多轮追问。

## 会话状态

每个会话建议保存以下状态：

- `session_id`
- `current_city`
- `original_query`
- `current_route`
- `confirmed_preferences`
- `confirmed_constraints`
- `turn_count`
- `turn_mode`
  - `generate`
  - `clarify`
  - `modify`
  - `confirm`
- `last_intent`
- `last_clarification`

状态只保存“对下一轮决策有用”的内容，不保存长篇自由文本。

## 每轮输入怎么处理

每一轮用户输入先被分类成下面几种之一：

- 新需求
- 补充信息
- 修改路线
- 确认当前方案
- 继续追问
- 重置会话

然后再把这轮输入转成结构化 patch。

## patch 格式

建议把“修改路线”统一成 patch，而不是重新从零生成。

示例：

```json
{
  "budget_delta": "down",
  "pace": "relaxed",
  "avoid_queue": true,
  "prefer_indoor": true,
  "add_categories": ["coffee"],
  "remove_categories": ["shopping"]
}
```

这样用户说：
- “太贵了”
- “再轻松一点”
- “不要排队”
- “换成室内”

都可以变成同一类结构化改动。

## 什么时候澄清

只在这些情况澄清：

- 关键槽位缺失，比如城市完全不明确
- 需求冲突，比如预算很低但又要求很多高消费点
- 偏好过于模糊，直接生成会明显失真
- LLM 置信度低，而且后续决策会被明显影响

澄清原则：
- 只问一个最关键的问题
- 只给 2 到 3 个选项
- 最多一轮
- 用户如果不想选，就走保守默认值

## 什么时候直接改，不澄清

这些情况不需要追问，直接按 patch 处理：

- “太贵了”
- “再轻松一点”
- “不要排队”
- “换成室内”
- “多加一个咖啡点”
- “少绕路”

这些都属于明确修改，应该直接更新当前路线。

## 多轮记忆边界

建议只记这些：

- 当前路线
- 当前确认过的偏好
- 当前确认过的约束
- 当前澄清问题和答案
- 当前会话模式

不建议记：

- 大段自由聊天原文
- 过长历史上下文
- 已经失效的旧方案全文

这样可以减少 token，也让系统更稳。

## 路由策略

推荐顺序：

1. 先识别这轮是不是修改
2. 再识别是不是补充信息
3. 再识别是不是澄清回答
4. 再识别是不是新需求
5. 最后才考虑重置或确认

这样能保证用户不断改需求时，不会被系统误判成“重新开始”。

## 评价标准

多轮是否做得好，主要看四点：

- 用户能不能连续修改路线
- 每次修改后路线变化是否符合预期
- 是否频繁误触发澄清
- token 和工具调用是否足够克制

## 结论

这套多轮方案不依赖 LangChain / ReAct 作为核心。
如果未来工具和步骤更多，可以再把它外层接成编排框架；
但在当前阶段，最重要的是把状态、patch、澄清和回放做扎实。
