# 优化优先级清单

这份清单只回答一件事：现在先优化什么，后面再优化什么，哪些东西先不要碰。

## 总原则

- 先补能直接提升用户体验和推荐质量的地方。
- 先做能验证、能回归、能解释的优化。
- 不要为了“看起来先进”而上重框架。
- 任何新能力都要能落到具体字段、具体流程、具体回归样例。

## 第一优先级：记忆和画像

这是后面“越用越懂用户”的核心。

### 先做什么
- 会话记忆
- 路线版本记忆
- 用户画像字段
- 行为信号记录
- 衰减和冲突规则

### 为什么先做
- 这是提升个性化最直接的地方。
- 路线修改、收藏、复制、澄清都能反哺画像。
- 记忆系统一旦立住，后续优化都更顺。

### 交付目标
- 用户再次打开时能默认带出稳定偏好。
- 用户连续修改路线时，系统能记住当前上下文。
- 用户收藏/修改行为能逐步沉淀画像，而不是只停留在单次会话。

---

## 第二优先级：路线修改和多轮 patch

这是路线类产品的核心体验。

### 先做什么
- 把“太贵了 / 更轻松一点 / 不要排队 / 换成室内”统一成 patch
- 路线版本化
- 修改前后差异可回放
- 轻量澄清只保留一轮

### 为什么先做
- 用户最常用的不是“重新生成”，而是“改一下”。
- 多轮对话如果没有 patch，会很快变成混乱的重算。

### 交付目标
- 每次修改都能明确知道改了什么。
- 修改后路线变化足够明显。
- 用户能看懂“为什么变了”。

---

## 第三优先级：标签、词典和回归

这是让 LLM 更容易分类、更少瞎猜的基础设施。

### 先做什么
- 补高置信 alias
- 扩 `intent_lexicon`
- 保持 `capabilities.json` 少而稳
- 扩 `eval_cases.json`
- 维护 `unclassified_clues`

### 为什么先做
- 你已经确认过标签覆盖不够宽。
- 这块是首用体验的关键。
- 回归样例越完整，后面越不容易改坏。

### 交付目标
- 用户第一次说常见口语时，系统能直接落到稳定标签。
- 新增一个表达时，能同步进入回归样例。

---

## 第四优先级：POI 和地图对齐

这是让路线“看起来对”变成“地理上也可信”的关键。

### 先做什么
- POI 字段对齐
- 高德事实校验
- 地址、经纬度、provider id 补全
- 规划结果和地图结果合并

### 为什么先做
- 用户对路线可信度很敏感。
- POI 数据如果不稳，路线再聪明也会显得虚。

### 交付目标
- 路线点位和真实地图尽量一致。
- 能输出真实路径、真实时长、真实距离。

---

## 第五优先级：前端交互继续收口

这是提升体验，但不该压过核心决策层。

### 先做什么
- 推荐区动态化
- 地图主视觉强化
- 方案切换更清楚
- 修改入口更顺手
- 知识解释更轻量

### 为什么先做
- 这会直接影响首屏感受和可理解性。
- 但它不应该抢掉后端决策的优先级。

### 交付目标
- 首页一眼能看懂怎么开始。
- 路线页一眼能看懂怎么改。

---

## 第六优先级：工程化收口

这是为了后续维护，不是为了短期演示。

### 先做什么
- capability registry 继续收口
- policy 配置化
- trace 字段标准化
- 接口契约统一
- 文档入口继续保持单一索引

### 为什么放后面
- 这些不会直接改变用户第一感受。
- 但会决定后面能不能稳定迭代。

### 交付目标
- 改 prompt、改权重、改标签时，不需要改散落代码。
- 所有关键变化都能追踪。

---

## 暂时不要优先做的事

- 不要先上完整 LangChain / ReAct 作为主框架
- 不要先拆微服务
- 不要先把所有文本都灌进重型 memory hub
- 不要先做语义穷举式标签库
- 不要先把 `capabilities.json` 变成长尾表达黑洞

## 一句话建议

如果现在要选一个最值得先做的方向，优先级是：

1. 记忆和画像
2. 多轮 patch 和路线版本
3. 标签和回归
4. POI 和地图对齐
5. 前端交互收口
6. 工程化收口
