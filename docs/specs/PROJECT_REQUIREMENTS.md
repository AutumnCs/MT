# 项目要求整理

这份文档把题目要求和实现目标单独拎出来，方便后续开发对齐。

## 1. 问题背景

用户在出行、游玩、约会、临时安排时，常常面对这些问题：

- 目的地不是单点，而是多个 POI 的组合
- 预算、时间、排队、距离、偏好会互相冲突
- 用户表达需求通常是自然语言，而不是结构化条件
- 用户真正需要的是一条可以直接执行的路线，而不是一堆推荐点

## 2. 核心任务

项目要做的是：

> 把用户的自然语言需求，转成一条满足时间、预算、偏好和路线顺序约束的可执行路线。

完整流程应包括：

1. 用户输入游玩或出行目标
2. 系统解析需求和约束
3. 结合 POI 数据、服务信息和内容信号召回候选点
4. 对候选点做多维评分和排序
5. 生成完整路线方案
6. 支持用户继续修改条件并重新规划

## 3. 交付目标

### 3.1 路线生成

- 能根据用户意图自动串联多个 POI
- 能生成完整路线安排
- 至少形成一条可执行路线

### 3.2 多条件与个性化

- 能处理预算、时间、排队、距离等差异化约束
- 能结合用户偏好生成差异化方案

### 3.3 动态调整

- 用户可以在结果页继续输入修改意见
- 系统可以根据修改意见重新规划路线

## 4. 评审重点

评审主要看三类能力：

### 4.1 完整性

- 路线是否真实可执行
- 时间安排是否合理
- POI 覆盖是否准确
- 是否满足多约束

### 4.2 创新性

- 是否支持自然语言交互
- 是否支持动态修改
- 是否体现 LLM + 数据 + 规则 + 排序 的融合

### 4.3 应用效果

- 页面是否完整
- 系统是否能稳定演示
- 结果是否有可解释性
- 文档是否完整、结构是否清晰

## 5. 关键约束

根据当前题目整理，建议把以下要求作为硬指标：

- 路线生成响应时间尽量控制在 `10 秒` 内
- 路线至少支持 `3 个 POI` 串联
- POI 类型至少覆盖 `餐饮 + 娱乐/文化` 等多类
- 路线要支持时间、预算、偏好等条件动态调整
- 路线要尽量“直接用、不踩雷”，不要太绕

## 6. 系统分工建议

### 6.1 LLM 负责

- 理解用户自然语言
- 把模糊需求转成结构化意图
- 帮助解释路线为什么这么排

### 6.2 数据负责

- 提供 POI 基础信息
- 提供标签、评分、营业时间、价格、经纬度等事实字段
- 提供偏好适配所需的业务信号

### 6.3 规则负责

- 控制预算、时间、城市、营业时间等硬约束
- 控制不可行路线的过滤

### 6.4 排序和规划负责

- 对候选 POI 打分
- 生成路线顺序
- 平衡“少绕路 / 高匹配 / 少排队 / 低预算”等目标

## 7. 对当前项目的落点

当前实现已经覆盖了这些方向：

- 自然语言输入
- LLM 解析与规则回退
- 本地 POI 检索
- 多维打分
- 多候选路线生成
- 二次修改
- 前端结果展示

后续最值得继续补的，是：

1. 扩充 POI 数据
2. 强化路线解释
3. 增加离线评估
4. 做更稳定的修改流程
5. 再接地图 API
