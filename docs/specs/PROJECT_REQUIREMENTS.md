# 项目要求与实现对齐

## 1. 官方任务目标

本赛题为“现在就出发：AI 本地路线智能规划”。任务背景是：用户在出行或游玩时，往往需要将多个目的地串联成高效路线，同时面对“想吃好又不想排队、时间预算二选一”等多重决策负担。现有搜索和推荐体验需要用户反复筛选、自行组合，决策成本高。

官方探索方向是：利用大语言模型，结合点评 POI 数据、UGC 智慧和用户个性偏好，自动生成可以直接执行的个性化路线方案。

## 2. 官方交付目标

### 路线生成

根据用户意图自动串联多个 POI，生成完整路线安排。

### 多条件与个性化

满足差异化条件约束，结合用户历史偏好生成差异化方案。

### 体验和约束

- 路线生成响应时间目标：小于 10 秒。
- POI 类型：至少覆盖餐饮 + 娱乐/文化两类。
- 路线规模：支持不少于 3 个 POI 串联。
- 重点关注：路线可用性、多约束满足、体验创新、技术创新、应用效果。

## 3. 当前实现覆盖

### 自然语言理解

- 支持自然语言输入。
- 支持显式城市选择。
- 支持 LLM-first 解析。
- 支持本地词典和 schema 归一化。
- 支持预算、时间、偏好、避让项、交通方式和必去点解析。
- 支持需求过泛时的一轮轻量澄清。

### 路线生成

- 从本地 POI 数据召回候选。
- 使用多因子排序选择更合适 POI。
- 使用 Beam Search 与启发式补全生成多站路线。
- 输出推荐方案、偏好优先版和紧凑少走版。
- 统计总花费、总时长、总距离和站点数。
- POI 类型覆盖餐饮、咖啡、展览、博物馆、夜景、街区、公园、购物、景点等。

### 动态修改

- 支持基于当前路线继续修改。
- 修改请求会继承当前路线意图。
- 支持“太贵了”“不要排队”“更轻松一点”“换成室内点”等增量约束。
- 响应 trace 中记录修改前后的站点变化。

### 可解释性

- 展示系统理解。
- 展示每站推荐理由。
- 展示站点顺序理由。
- 展示路线提醒和风险提示。
- 展示解析来源、识别信号、未归类线索和地图状态。

### 地图预览

- 后端封装天地图服务。
- 未配置地图 key 时使用本地经纬度估算兜底。
- 前端可展示 marker、polyline、路线范围和地图来源。

### 评测

- 提供离线评测集和评测脚本。
- 当前 25 个用例覆盖意图解析和路线修改。
- 最近一次本地运行结果为 25/25 通过。

## 4. 评审关注点对齐

### 完整性

项目已经形成完整闭环：输入、解析、召回、排序、规划、展示、解释、修改和记录。

对应官方关注：

- 路线是否合理可执行。
- 时间安排是否现实。
- POI 覆盖是否准确。
- 能否同时兼顾时间、距离、偏好、排队等约束。

### 创新性

项目将 LLM 意图解析与确定性路线规划解耦，既保留自然语言入口的灵活性，又保留后端算法的可控性和可解释性。

对应官方关注：

- 支持自然语言实时调整。
- 支持反馈闭环。
- 支持多方案对比。
- 体现 LLM + POI/UGC + 搜索/规划算法的融合。

### 应用效果

前端展示不是纯文本，而是路线工作台。用户可以查看路线摘要、时间线、多方案、地图预览、诊断信息和修改入口。

对应官方关注：

- 方案完整。
- 可演示。
- 文档清晰。
- 具有继续扩展和维护空间。

### 工程可扩展性

后端模块按职责拆分，排序权重配置化，词典独立维护，评测脚本可用于回归检查。

## 5. 当前口径

- 当前城市：广州、上海。
- 当前 POI：`pois.json` 中 125 个地点。
- 当前地图：天地图优先，本地兜底。
- 当前评测：离线规则链路 25/25 通过。
- 当前路线策略：推荐方案、偏好优先版、紧凑少走版。

## 6. 比赛报告建议重点

- 讲清楚系统不是“地点推荐”，而是“自然语言到多站路线”的规划系统。
- 讲清楚 LLM 只负责意图入口，后续规划由可解释算法完成。
- 讲清楚 POI 排序的多因子设计。
- 讲清楚 Beam Search 路线组合如何兼顾偏好和转场。
- 讲清楚路线修改如何继承上下文。
- 讲清楚地图服务可降级，保证演示稳定。
- 讲清楚评测结果和后续算法展望。
- 少强调底层文件结构、key 配置、兼容 wrapper 等不直接体现创新的工程细节。
