# MeituanAgent 技术报告初稿

## 1. 项目背景

本项目面向“本地生活路线规划”场景，目标不是简单返回一组 POI，而是根据用户的自然语言需求，生成一条可以执行、可以解释、可以修改的城市路线。

真实用户的表达通常并不规整，例如：

- 多看几个景点，顺便喝个早茶
- 想轻松一点，别太赶，也别排太久
- 想拍照，但不要太便宜
- 第一天先吃饭，后面再逛一逛，最后看夜景

这些需求同时包含城市、时间、预算、偏好、避让、顺序和强弱关系。如果直接用传统关键词检索，系统很容易只能返回单个地点；如果完全交给大模型端到端生成，又容易出现不可控、不可验证、结果不稳定的问题。

因此，本项目采用“LLM 语义理解 + 系统归一化 + 可解释规划”的混合方案，让模型负责理解自然语言，让系统负责约束、排序、组合和校验。

## 2. 总体架构

系统采用前后端分离架构：

- 前端使用 Flutter，提供自然语言输入、城市选择、偏好选择、路线结果、路线修改、解释和地图预览。
- 后端使用 FastAPI，负责意图解析、POI 召回、排序、路线规划、结果解释、上下文记忆和离线评测。

后端核心链路如下：

1. 用户输入自然语言需求。
2. 系统先做本地轻量解析，提取城市、偏好、预算、时间、避让项等信息。
3. 如果需求简单且置信度高，直接走本地快速路径。
4. 如果需求复杂、冲突多或表达过于模糊，则调用 LLM 输出结构化意图。
5. LLM 输出不会直接参与规划，而是进入统一 schema 做归一化。
6. 系统基于结构化意图召回候选 POI，并通过多因子排序生成路线。
7. 路线校验器检查数量、顺序、预算、类别覆盖和必须项。
8. 结果解释模块将内部决策转换成用户可理解的说明。

这种结构的好处是：LLM 擅长理解语言，系统擅长控制结果。两者分工明确，既保留泛化能力，也保留可维护性。

## 3. 核心创新点

### 3.1 对话式输入 + 结构化输出

项目没有把用户交互做成死板表单，而是保留自然语言入口。用户可以像聊天一样表达需求，系统再把这些需求转成结构化路线任务。

同时，输出并不是只给一条路线，而是给出：

- 主方案
- 备选方案
- 路线解释
- 风险提示
- 修改入口

这使产品既有对话式体验，也有规划工具的可操作性。

### 3.2 主目标 / 次目标分层表达

以前很多系统会把意图扁平化成一串标签，结果是“饭店、景点、公园、咖啡”都混在一起，系统很难判断谁是主线、谁是补充。

本项目改成了分层表达：

- `primary_categories`：主目标
- `secondary_categories`：次目标
- `goal_summary`：一句话概括需求
- `uncertain_fields`：不确定项
- `needs_clarification`：是否建议追问

这样做的结果是，系统可以区分“多看几个景点”与“顺便喝早茶”的主次关系，而不是把所有信号平均处理。

### 3.3 修改路线是增量而不是重算

很多路线产品只支持重新生成，用户一旦提出修改，前面确认过的约束就可能丢失。

本项目把修改视为增量操作：

- 保留原路线的城市、偏好、避让项和数量约束
- 叠加新修改意图
- 重新排序和重组
- 输出变化记录

这样用户连续修改时，系统不会“忘掉前文”，体验更接近真实对话。

### 3.4 可解释的多因子排序

POI 选择不是单一分数排序，而是多因子融合：

- 类别匹配
- 偏好匹配
- 避让项惩罚
- 预算适配
- 停留时长
- 顺序合理性
- 片区聚合
- 风险项（排队、过远、价格偏高等）

每个 POI 都能说明“为什么高分”“为什么在这个位置”，这对于竞赛答辩和产品可维护性都很重要。

## 4. 意图理解与泛化能力

### 4.1 为什么不能只靠硬规则

如果系统完全依赖词表，会出现两个问题：

1. 覆盖范围有限，用户换一种说法就失效。
2. 维护成本会不断上升，后面变成无底洞。

因此，本项目没有把泛化能力寄托在无限补词表上，而是采用三层方式：

- 词表只保留少量高置信锚点
- LLM 负责理解长尾表达
- 系统负责归一化和约束控制

### 4.2 语义桥与向量化

系统中加入了轻量语义桥：

- 统一同义表达
- 对用户长尾描述做轻量向量召回
- 将用户输入、POI 文本、评论信息和路线说明映射到同一语义空间

这让系统不必只依赖关键词命中，而是能够处理“松弛感”“烟火气”“轻松一点”“不要太赶”这类口语表达。

### 4.3 澄清机制

当用户表达过于模糊时，系统不会强行猜一个结果，而是会主动发起澄清。

这是为了避免两类问题：

- 过度自信地生成错误路线
- 用户后续频繁改动，导致体验更差

澄清机制只问一个关键问题，避免把产品做成复杂问卷。

## 5. 路线规划算法

### 5.1 POI 召回

首先根据用户意图从本地 POI 库中召回候选点。召回不仅看类别，也看文本语义、标签、评论信号和地理信息。

### 5.2 POI 排序

排序阶段综合考虑：

- 用户偏好强度
- 类别匹配
- 预算适配
- 排队风险
- 停留时长
- 顺路程度
- 片区聚合

这个阶段的目标不是“最热门”，而是“最适合当前需求”。

### 5.3 路线组合

路线规划不是简单取 Top-K，而是要把多个 POI 串成一条顺序合理的路线。

系统会考虑：

- 哪些点适合作为开场
- 哪些点适合作为中段过渡
- 哪些点适合作为收尾
- 哪些点适合和前后站连成同一区域
- 哪些点应当避开高峰或拥堵

因此，路线结果不是点的集合，而是一条有节奏、有顺序、可执行的路径。

### 5.4 路线修改

修改阶段的重点是保留原有路线结构，再做增量修正。比如用户说“加个早茶，别排太久”，系统会：

- 保留原先景点主线
- 增加餐饮需求
- 降低高排队 POI 权重
- 重新安排顺序

这比完全重算更符合真实使用场景。

## 6. 解释与前端体验

系统输出不仅有路线，还包括解释。

前端展示的内容主要有：

- 为什么选这些点
- 为什么这样排序
- 哪些偏好被满足了
- 哪些约束被保留了
- 哪些地方存在风险
- 如果想改，应该往哪个方向改

这对用户体验很重要，因为用户不只是想拿结果，还想知道系统是不是“听懂了自己”。

## 7. 上下文与画像

项目实现了轻量上下文和用户画像能力，记录的不是原始聊天内容，而是可用于规划的结构化信号，例如：

- 最近的需求类型
- 常见偏好
- 常见避让项
- 节奏偏好
- 城市与类别偏好

这样设计有两个好处：

1. 能帮助后续路线推荐更贴近用户习惯。
2. 不会把用户画像做成不可控的聊天记录堆积。

## 8. 评测结果

项目配套了离线评测集，用于验证：

- 意图解析是否稳定
- 路线生成是否满足约束
- 路线修改是否保留原有意图
- 边界场景是否仍能正确处理

当前离线回归已覆盖 46 个核心用例，最近一次回归结果为 46/46 通过，覆盖意图解析、路线修改、workflow trace、memory opt-out/session 行为、路线版本持久化、路线 delta 摘要、session route autofill、热度/排队工具调度、路线质量、失败边界、intent repair，以及 <10 秒响应、≥3 POI、餐饮 + 文化/娱乐覆盖和完整时间表的验收型用例，说明当前方案在已覆盖场景中是稳定的。

## 9. 工程化设计

为了保证后续可维护性，项目把功能拆成了明确的模块：

- `core`：schema、意图、提示词、LLM 和语义桥
- `services`：召回、排序、规划、解释、校验、上下文、地图
- `eval`：评测和回归
- `policy`：策略参数

这种拆法的价值在于：

- 新能力可以按层加入
- 出问题时容易定位
- 改算法不必大面积改 UI
- 文档和代码更容易对齐

## 10. 未来优化方向

后续如果继续增强，可以重点做以下几件事：

1. 继续扩充高质量评测集，覆盖更多真实表达。
2. 引入更强的向量化检索模型，增强长尾泛化能力。
3. 逐步完善 POI 语义知识库，但避免变成大而全词库。
4. 进一步强化路线修改的多轮上下文能力。
5. 在不牺牲可解释性的前提下，优化召回和排序效率。
6. 如果后续数据规模更大，再考虑更重的 Agent 工作流或更强的检索增强框架。

## 11. 总结

本项目的核心价值不在于“把地图点列出来”，而在于把用户模糊、口语化、带约束、可修改的行程需求，转换成一条可执行、可解释、可迭代的路线。

它的技术路线不是单纯依赖规则，也不是完全依赖大模型，而是把两者的优点结合起来：

- LLM 提供泛化理解能力
- 结构化 schema 提供稳定边界
- 规划与校验模块提供可执行性
- 解释模块提供可理解性

这也是本项目最重要的创新点。
