# MeituanAgent 详细技术报告底稿

> 本文档用于比赛技术报告扩写、PPT 生成和答辩材料整理。内容基于当前代码实现、数据结构和本地评测结果撰写，尽量避免无法由项目支撑的夸大表达。

## 1. 项目背景与问题定义

本地生活路线规划是一个典型的多约束决策问题。用户在真实出行前，往往不会只问“附近有什么好吃的”或“哪里适合拍照”，而是会提出一组混合需求。例如：

- “广州周末半天，想轻松一点，吃点好的，不要排队。”
- “上海晚上想看夜景，顺便喝杯咖啡，别太赶。”
- “雨天想找室内点，适合朋友一起逛，预算 200 左右。”
- “第一站先吃饭，饭后想去大学城附近逛逛，最后看夜景。”

这些表达通常同时包含城市、时间、预算、起点、偏好、避让项、路线节奏、交通方式和隐含顺序。如果只做传统地点搜索，系统往往只能返回一组独立 POI，不能回答“这些地点如何串成一条可执行路线”。如果只让大模型直接生成文字路线，又会面临结果不可验证、地点属性不稳定、路线距离不可控、修改难以继承上下文等问题。

MeituanAgent 的设计目标是：让用户用自然语言表达出行想法，系统将其转化为结构化意图，再结合本地 POI 数据、可解释排序算法和路线组合算法，生成一条可执行、可切换、可解释、可继续修改的城市路线。

项目当前已经实现从输入到输出的完整闭环：

- Flutter 前端提供自然语言入口、城市选择、偏好选择、路线结果页、澄清页、解释页和修改入口。
- FastAPI 后端提供意图解析、路线生成、路线修改、上下文记录、评测接口和地图预览接口。
- 本地 POI 数据包含 125 个地点，覆盖广州和上海。
- 后端路线链路包含 POI 召回、多因子排序、Beam Search 路线组合、多方案生成、解释生成和 trace 诊断。
- 离线评测脚本当前 25 个评测用例全部通过。

## 2. 系统总体架构

MeituanAgent 采用前后端分离架构。前端负责交互表达和路线工作台展示，后端负责智能解析和路线规划。

### 2.1 前端架构

前端基于 Flutter 实现，主要模块包括：

- `lib/main.dart`：应用入口和路线输入首页。首页包含城市选择、自然语言输入框、快速偏好标签、推荐灵感和功能介绍。
- `lib/pages/route_result_page.dart`：路线结果工作台。展示路线摘要、系统理解、多策略方案、时间线、路线提醒、诊断信息和二次修改入口。
- `lib/pages/clarification_page.dart`：澄清页。当后端判断用户需求过泛时，前端展示一个关键问题和若干选项。
- `lib/pages/knowledge_explanation_page.dart`：解释页。用于展示系统理解和路线推荐逻辑。
- `lib/services/route_api_service.dart`：封装前端对后端 API 的调用。
- `lib/widgets/route_map_view.dart`：路线地图预览组件。

前端不是单纯聊天窗口，而是“对话式入口 + 结构化路线工作台”。这种设计保留了自然语言输入的低门槛，同时让路线结果以可读、可比、可修改的形式呈现。

### 2.2 后端架构

后端基于 FastAPI 实现，入口位于 `backend/main.py`。主要接口包括：

- `/api/intent/parse`：解析用户意图。
- `/api/route/generate`：根据自然语言需求生成路线。
- `/api/route/modify`：基于已有路线进行增量修改。
- `/api/context/{session_id}`：读取上下文和用户画像。
- `/api/eval/run`：运行离线评测。
- `/api/map/status`、`/api/map/geocode`、`/api/map/route`、`/api/map/preview`：地图相关能力。

核心服务层包括：

- `services/route_service.py`：路线规划总编排，负责连接意图解析、澄清判断、约束校验、POI 召回、排序、路线规划和响应生成。
- `core/intent_parser.py`：本地规则解析、LLM 结果归一化、UI 偏好合并、修改提示解析。
- `services/poi_retriever.py`：从本地 POI 数据中进行候选召回。
- `services/ranker_engine.py`：POI 多因子排序和推荐理由生成。
- `services/route_planner.py`：路线组合、多方案生成、站点顺序优化和时间安排。
- `services/response_generator.py`：将内部路线对象转换成前端可展示响应，并生成站点解释、风险提示和 trace。
- `services/context_service.py`：会话事件、路线版本和轻量用户画像存储。
- `services/map_service.py`：天地图 API 封装和本地地图兜底逻辑。

### 2.3 数据流

完整路线生成流程如下：

1. 用户在 Flutter 首页输入自然语言需求，并可选择城市和偏好标签。
2. 前端先尝试调用意图解析接口，用于合并解析偏好和城市。
3. 前端调用 `/api/route/generate` 提交路线生成请求。
4. 后端读取 session 上下文和轻量画像。
5. 后端使用 LLM-first 路径解析用户意图，并通过本地规则进行归一化补充。
6. 如果需求过泛，后端返回澄清响应。
7. 如果需求足够明确，后端进行约束校验。
8. 后端从 `pois.json` 中召回候选 POI。
9. 后端对候选 POI 进行多因子排序。
10. 路线规划器基于排序结果生成推荐方案和备选方案。
11. 响应生成器输出路线摘要、站点时间线、解释、风险提示、地图预览和诊断 trace。
12. 前端进入路线工作台展示结果。
13. 用户可以继续输入修改需求，前端调用 `/api/route/modify`，后端基于当前路线做增量重排。

## 3. 功能设计

### 3.1 自然语言输入

系统允许用户直接用自然语言表达路线需求。相比表单式输入，自然语言入口更贴近用户真实表达方式。用户不需要逐项填写城市、预算、时间、类型和偏好，而是可以用一句话描述。

系统支持解析的主要信息包括：

- 城市：目前支持广州和上海。
- 起点：例如“从广州塔出发”。
- 时间：例如“下午两点”“晚上 9 点前结束”。
- 预算：例如“预算 200”“人均 150 元”。
- 类别：例如餐饮、咖啡、夜景、街区、公园、购物、展览、博物馆。
- 偏好：例如拍照、约会、亲子、朋友、独行、轻松、安静、本地特色、雨天、室内、citywalk。
- 避让项：例如不想排队、别太远、避开拥挤、不吃辣。
- 交通方式：步行、地铁、打车、混合。
- 必去点：例如广州塔、外滩、大学城等。
- 阶段顺序：例如先吃饭、饭后夜景、第一站图书馆、最后收尾。

### 3.2 快速偏好与城市选择

前端首页提供城市选择和快速偏好标签。城市选择用于显式限定 POI 数据范围，偏好标签用于降低用户输入成本。偏好标签被选中后，会自动补充到输入框，并作为请求参数传给后端。

当前快速偏好包括约会、拍照、不想排队、性价比、轻松路线、美食、文艺、夜景等。这些标签在后端会被映射到稳定偏好键，例如 `couple`、`photo`、`avoid_queue`、`value`、`relaxed`、`food`、`culture`、`night_view`。

### 3.3 一轮澄清机制

当用户需求过于宽泛时，系统会先提出一个关键澄清问题，而不是直接生成路线。后端会统计当前意图中的强信号数量，包括偏好、类别、必去点、预算、时间和起点。如果强信号不足，并且 query 中出现“随便”“看看”“安排一下”“都可以”等模糊表达，系统会返回澄清响应。

澄清设计遵循两个原则：

- 只问一个关键问题，避免把产品变成复杂问卷。
- 选项必须能直接影响路线规划，例如美食为主、拍照为主、轻松逛街、更近一点、少排队一点、预算更低。

这一机制能提升首条路线的稳定性，也能让系统在不确定时主动降低错误生成风险。

### 3.4 路线生成与多方案切换

路线生成不是返回单个地点，而是返回一条包含多个站点的完整路线。每个站点包含 POI 信息、到达时间、离开时间、停留时间、推荐理由、风险提示和转场信息。

系统会生成主方案和备选方案。当前实现中，路线规划器会生成：

- 推荐方案：综合考虑偏好、距离、预算、时间和类别覆盖。
- 偏好优先版：更重视 POI 与用户偏好的匹配。
- 紧凑少走版：更重视低转场和少走路。

前端结果页支持方案切换。用户可以比较不同方案的总预算、总时长、总距离、站点数和路线站点。

### 3.5 路线解释

系统强调结果可解释。后端会生成两类解释：

- 路线级解释：例如“为你规划了一条 6 站路线，总游览时间、交通时间、预计花费是多少”。
- 站点级解释：说明每个 POI 为什么被选中，以及为什么放在当前位置。

站点解释会结合类别匹配、偏好命中、预算匹配、排队风险、拍照/美食/文化分、顺序和转场距离。例如一个咖啡点可能被解释为“适合作为轻量开场，停留时间不长，也方便后续转场”；一个夜景点可能被解释为“放在最后，是因为夜景类地点越晚观赏性越强”。

### 3.6 路线修改

用户拿到路线后，可以继续输入修改需求，例如：

- “太贵了”
- “更轻松一点”
- “不要排队”
- “再紧凑一点”
- “多一点拍照点”
- “换成室内点”

后端修改接口会接收当前路线和修改文本。系统不会把修改请求当作全新请求，而是先继承当前路线中的城市、类别、偏好和避让项，再把本轮修改作为增量约束合并进去。

修改逻辑的关键点是：

- 继承已有路线意图，保持上下文连续性。
- 从修改文本中提取新的偏好和避让项。
- 对当前路线中可能需要替换的旧站点施加惩罚。
- 重新召回、排序、规划路线。
- 在响应 trace 中记录 added、removed、kept 等修改变化。

### 3.7 上下文与轻量画像

后端实现了轻量上下文系统，用于记录会话事件、路线版本和用户画像。上下文存储在 `.tmp/context_store.json`。

系统记录的信息包括：

- 最近 query。
- 最近意图摘要。
- 当前路线版本。
- 用户行为事件。
- 城市计数。
- 类别偏好计数。
- 偏好计数。
- 避让项计数。
- 节奏、交通、预算档位等行为统计。

用户画像只作为软偏置，不覆盖当前明确需求。例如用户多次选择慢节奏和少排队，如果下一次没有说明节奏，系统可以轻微偏向慢节奏；但如果用户明确说“高效一点”，当前请求优先。

### 3.8 地图预览

地图服务封装了天地图 API，并支持本地兜底。地图预览会输出：

- marker 列表。
- polyline 路线折线。
- bounds 地图边界。
- center 地图中心。
- segments 转场段。
- provider 和 coordinate_source 诊断信息。

如果配置了天地图密钥，系统会尝试通过天地图搜索和路线接口解析坐标、生成路线折线。如果没有密钥或接口不可用，系统使用本地经纬度和近似折线生成预览，保证比赛演示链路可用。

## 4. 算法设计

### 4.1 混合意图解析算法

意图解析采用 LLM-first 和本地规则归一化结合的方式。正式路线生成路径中，后端优先调用 LLM 解析用户 query；如果评测环境设置 `LLM_INTENT_DISABLE_LLM=1`，则使用本地规则解析。

本地解析器支持：

- 城市识别：直接识别广州、上海，也可通过地标反推城市。
- 时间解析：支持中文时间、数字时间和 `HH:MM` 格式。
- 预算解析：支持阿拉伯数字和中文数字预算。
- 起点解析：支持“从 XXX 出发/开始”。
- 类别识别：通过词典识别咖啡、美食、图书馆、展览、夜景、街区、公园、购物、博物馆、景点等。
- 偏好识别：识别约会、拍照、美食、文化、本地特色、夜景、安静、雨天、步行、亲子、咖啡、朋友、独行、性价比、室内、室外、购物、citywalk、高效、紧凑等。
- 避让项识别：识别不吃辣、别太远、不要排队、避开拥挤等。
- 节奏识别：输出 `fast`、`normal`、`slow`。
- 交通方式识别：输出 `walking`、`metro`、`taxi`、`mixed`。
- 必去点识别：从城市地标词典中提取。
- 未归类线索提取：保留 `vibe`、`松弛感` 等长尾表达。

LLM 输出不会直接进入路线规划，而是经过 `normalize_llm_intent` 归一化。归一化过程会校验城市、预算、类别、偏好、避让项、节奏和交通方式，并与本地解析结果合并。这样可以降低 LLM 解析漂移对规划链路的影响。

### 4.2 意图派生字段同步

`ParsedIntent` 采用列表字段作为主要表示，例如 `preferences`、`avoid`、`required_categories`。为了兼容已有排序和筛选逻辑，模型内部还同步生成布尔字段，例如 `prefer_photo`、`prefer_food`、`avoid_queue` 等。

派生字段包括：

- `intent_tags`：由类别、偏好、避让项和必去点合并而来。
- `soft_preferences`：用于画像和上下文软偏置。
- `preferred_categories`：用于排序阶段的类别偏好。
- `recognized_signals`：用于前端诊断展示。
- `hard_constraints`：记录城市、预算、时间、起点等硬约束。

这种设计让系统既能保持新 schema 的灵活性，又能兼容已有基于布尔字段的规则逻辑。

### 4.3 POI 召回算法

POI 召回位于 `services/poi_retriever.py`。召回步骤如下：

1. 从 `pois.json` 加载所有 POI，并缓存为 Pydantic 对象。
2. 根据城市过滤候选。如果用户没有指定城市，则不做城市约束。
3. 检查 `must_include` 和 `start_location`，优先召回名称、地址、商圈、片区、标签或评论中匹配的 POI。
4. 根据 `required_categories` 和 `preferred_categories` 召回类别匹配 POI。
5. 根据 `preferences`、`soft_preferences`、`unclassified_clues` 和 `must_include` 做文本匹配召回。
6. 如果召回结果不足，则从同城 POI 中补充高分候选。

召回打分 `_recall_score` 会考虑：

- 类别命中：必要类别加高分，偏好类别加次高分。
- 文本命中：用户偏好、类别、长尾线索出现在 POI 文本中加分。
- 室内外匹配：雨天或室内偏好匹配加分。
- 安静/低排队匹配：低排队等级加分，高排队等级扣分。
- 预算匹配：POI 人均价格相对预算合理则加分，明显超出则扣分。
- 起点/必去点匹配：强加分。
- 评分质量：高评分有额外加分。

召回阶段的目标不是最终排序，而是尽量给排序器提供足够丰富且不偏离需求的候选集合。

### 4.4 POI 多因子排序算法

POI 排序位于 `services/ranker_engine.py`。排序模型是可解释的加权评分系统，权重来自 `policy/poi_ranker_weights.json`。

每个 POI 会计算多个子分：

- `preference_match_score`：偏好匹配分。根据用户偏好和 POI 标签、适用人群、评论信号计算。
- `semantic_score`：语义分。根据拍照、约会、美食、文化、本地特色、雨天、夜景、安静等评论信号计算。
- `rating_score`：评分分。根据 POI 评分相对基线归一化。
- `category_match_score`：类别匹配分。判断是否属于用户必要类别或偏好类别。
- `budget_score`：预算适配分。根据人均价格与预算均摊值的差异计算。
- `time_suitability_score`：时间适配分。根据用户节奏和 POI 停留时长计算。
- `queue_penalty`：排队惩罚。排队风险越高惩罚越大，若用户明确避开排队则惩罚加倍。
- `crowd_penalty`：拥挤惩罚。拥挤风险越高惩罚越大，若用户偏好安静则惩罚加倍。
- `price_penalty`：价格惩罚。明显超过预算时扣分。
- `modification_penalty`：路线修改时的额外惩罚。若用户要求替换或避让当前路线中的某些特征，则降低旧站点分数。

最终分数由正向分加权求和，再减去惩罚项。排序结果包含：

- `poi`：POI 对象。
- `final_score`：最终得分。
- `score_breakdown`：各项子分。
- `rank`：排序名次。
- `recommend_reason`：推荐理由。

可解释排序是本项目的重要设计。它既方便调试，也方便答辩说明“为什么系统选了这些点”。

### 4.5 路线组合算法

路线规划位于 `services/route_planner.py`。核心目标是在有限时间和预算内，从排序后的 POI 中选择多个站点，并安排合理顺序。

路线规划过程包括：

1. 生成 `rank_map`，记录每个 POI 的排序信息。
2. 确定需要覆盖的类别。如果用户没有明确类别，则使用排序靠前 POI 的类别作为默认覆盖目标。
3. 识别强制站点，包括起点匹配点和 `must_include` 匹配点。
4. 选择锚点片区，尽量让路线集中在同一片区或相邻商圈。
5. 按类别选取初始候选，保证必要类别至少有一个 POI。
6. 使用 Beam Search 扩展路线。
7. 检查时间、预算和站点数约束。
8. 对候选路线评分，保留得分最高的若干路线状态。
9. 根据显式阶段约束调整顺序。
10. 构建带时间安排的 `RouteStop`。

Beam Search 扩展时会综合考虑：

- POI 最终排序分。
- 与上一站的距离得分。
- 是否属于锚点片区。
- 加入后总时长是否超过可用时间。
- 加入后总预算是否明显超出预算。
- 是否已经达到修改请求限制的站点数。

这种方法比简单 Top-N 更合理，因为它把“地点好不好”和“路线顺不顺”同时纳入考虑。

### 4.6 距离和交通时间估算

系统使用 Haversine 公式计算两个经纬度点之间的地面距离。交通时间估算会根据交通方式调整：

- `walking`：步行时间按距离乘以步行分钟/公里估算。
- `metro`：距离乘以较快系数，并加入进出站和等待时间。
- `taxi`：距离乘以打车时间系数，并加入起步等待。
- `mixed`：短距离按步行估算，长距离在地铁/打车估算中选择更稳的近似。

如果启用地图服务，部分路线可以使用天地图返回的距离、时间和 polyline。否则使用本地估算兜底。

### 4.7 路线评分算法

路线评分 `_score_route` 综合考虑：

- 时间适配度：总游览和交通时间是否接近可用时间。
- 交通效率：交通时间占总时间比例越低越好。
- POI 平均排名：选中的 POI 在排序结果中越靠前越好。
- 类别覆盖：路线是否覆盖足够多的体验类型。
- 夜景顺序：有夜景偏好时，夜景点放在末段更好。
- 时间平滑度：站点停留时间差异不要过大。
- 片区聚合度：同片区站点越集中，转场越自然。
- 预算适配度：总花费是否在预算内。
- 营业时间适配度：到达和离开时间是否落在营业窗口内。

最终方案排序还会优先考虑必去点覆盖率和必要类别覆盖率，避免高分路线漏掉用户硬约束。

### 4.8 显式阶段顺序处理

用户可能表达顺序需求，例如“第一站先去图书馆”“先吃饭”“饭后看夜景”“最后去广州塔”。系统在 `route_service.py` 中通过 `_apply_ordered_query_hints` 提取阶段线索，生成 `ordered_stages`。

路线规划后，`_apply_ordered_stages` 会根据阶段匹配分重新安排站点顺序。阶段匹配逻辑支持：

- `library`：图书馆或看书自习。
- `food`：餐饮。
- `night`：夜景。
- `quiet_rest`：清闲休息。
- `university_area`：大学城、小洲村、岭南印象园等区域。
- `play`：游玩、街区、景点、公园、展览等。

这种机制让顺序表达不只是普通关键词，而是真正影响路线结构。

### 4.9 响应解释算法

响应生成器会为每个站点生成原因。原因由两部分组成：

- 匹配原因：说明该 POI 如何满足用户偏好或约束。
- 顺序原因：说明该 POI 为什么放在当前路线位置。

匹配原因基于 POI 的类别、价格、评分、评论信号、排队等级、室内外属性和用户意图。顺序原因基于站点位置、上一站距离、同片区关系、餐饮/夜景等时间顺序逻辑。

例如：

- 咖啡点放在第一站，原因可能是停留时间短，适合作为开场。
- 餐饮点放在最后，原因可能是逛完后用餐更自然。
- 夜景点放在最后，原因可能是晚间观赏性更强。
- 与上一站同片区的点，原因可能是减少绕路和重复转场。

解释算法使路线结果可以被用户理解，也方便比赛答辩展示系统内部决策逻辑。

## 5. 核心创新点

### 5.1 对话式入口与结构化路线工作台结合

项目没有把产品做成纯聊天，也没有做成复杂表单。输入阶段采用自然语言，降低用户表达成本；输出阶段采用结构化路线工作台，展示路线摘要、方案切换、时间线、风险提示、解释和修改入口。

这种交互设计兼顾自然语言的灵活性和路线结果的可操作性。用户可以像聊天一样提出需求，又可以像使用规划工具一样比较和调整方案。

### 5.2 LLM 与确定性规划解耦

项目没有让 LLM 直接生成最终路线，而是将 LLM 放在意图解析入口。路线生成由后端确定性模块完成，包括 POI 召回、排序、路线组合和解释生成。

这种架构有几个好处：

- LLM 负责自然语言理解，发挥其语义泛化能力。
- 后端算法负责约束满足和路线可执行性。
- LLM 输出经过 schema 归一化，减少不可控结果。
- 排序和路线规划可调参、可评测、可解释。
- 当 LLM 不可用时，本地规则仍可用于测试和部分降级。

### 5.3 可解释多因子排序

POI 排序不是一个不可解释黑盒，而是由多个业务含义明确的子分组成。每个 POI 为什么得分高、为什么被惩罚、为什么推荐，都可以追溯到具体字段。

例如：

- 用户说“不想排队”，高排队等级 POI 会被扣分。
- 用户说“雨天”，室内或雨天适配分高的 POI 会加分。
- 用户说“拍照”，photo_score 高或评论中拍照信号强的 POI 会加分。
- 用户有预算，价格明显超出预算的 POI 会被惩罚。

这种设计适合比赛答辩，因为可以清楚解释算法逻辑，而不是只说“模型推荐”。

### 5.4 路线级组合搜索

项目不是简单取 Top-K POI，而是在路线级别做组合搜索。Beam Search 允许系统保留多个候选路线状态，并在时间、预算、距离、类别覆盖和片区聚合之间做平衡。

相比直接取前几个高分 POI，路线级搜索可以避免以下问题：

- 高分 POI 分布过远，导致路线不可走。
- 类别重复过多，体验单一。
- 忽略必去点或顺序需求。
- 总时长超过用户可用时间。
- 总预算超过用户预算。

### 5.5 增量修改机制

路线修改是项目的关键能力。很多路线产品只支持重新生成，而 MeituanAgent 支持基于当前路线继续调整。系统会继承当前路线意图，再叠加修改约束。

例如用户先生成了一条夜景路线，再说“不要排队”，系统会保留夜景、美食等原始需求，同时增加 `avoid_queue`，并降低高排队风险站点的得分。这种设计更符合真实多轮决策过程。

### 5.6 轻量记忆与软偏置画像

项目实现了会话上下文和轻量用户画像。它不是简单把历史聊天记录拼进 prompt，而是将行为结构化为城市、类别、偏好、避让项、节奏、交通和预算等统计信号。

画像只做软偏置，不覆盖当前显式需求。这一点很重要，因为用户今天的需求可能与历史偏好不同。软偏置设计使个性化更稳健，也更容易解释。

### 5.7 地图服务可降级

项目封装天地图能力，但不把外部 API 作为唯一依赖。在没有密钥或接口不可用时，本地经纬度距离估算和近似 polyline 仍能支撑路线展示。这种可降级设计提升了比赛现场演示的稳定性。

## 6. 工程实现细节

### 6.1 后端接口设计

后端接口围绕路线生成主链路设计：

- 解析接口负责将自然语言转为结构化意图。
- 路线生成接口负责完整规划。
- 路线修改接口负责多轮增量调整。
- 上下文接口负责读取和记录会话状态。
- 地图接口负责提供预览和外部地图能力。
- 评测接口负责快速检查离线质量。

每个接口都有明确输入输出模型，使用 Pydantic 做请求和响应校验。

### 6.2 数据模型设计

核心数据模型包括：

- `POI`：地点对象。
- `ParsedIntent`：解析后的用户意图。
- `RouteStop`：路线站点。
- `RouteResponse`：路线生成响应。
- `RouteDiagnostics`：诊断信息。
- `ContextSnapshot`：上下文快照。
- `UserProfile`：轻量用户画像。

POI 字段比较丰富，除了基础名称、地址、经纬度、类别外，还包括价格、评分、停留时长、营业时间、排队等级、室内外、评论关键词、正负面评论、评论信号、适用人群和片区信息。这些字段为可解释排序和路线规划提供了基础。

### 6.3 配置化策略

排序权重保存在 `backend/policy/poi_ranker_weights.json`。这种设计使算法参数可以独立调整，而不必修改核心代码。后续可以根据评测结果或用户反馈调整不同子分权重。

能力注册保存在 `backend/capabilities.json`，意图词典保存在 `backend/intent_lexicon.json` 和 `backend/lexicon/` 目录。能力和词典分离，有利于后续维护。

### 6.4 评测工具

评测工具位于 `backend/eval/`：

- `eval_runner.py`：运行评测用例。
- `check_quality.py`：一次性质量检查。
- `watch_quality.py`：监听文件变化并重复运行评测。

评测用例保存在 `backend/eval_cases.json`，覆盖意图解析和路线修改。评测脚本会设置 `LLM_INTENT_DISABLE_LLM=1`，用于验证本地规则解析和后续规划链路稳定性。

本地运行结果：

- 总用例数：25
- 通过用例数：25
- 通过率：1.0

这说明当前规则解析、召回、排序和路线规划链路在已有测试集上表现稳定。

## 7. 算法层面优化展望

### 7.1 层次化意图表示

当前意图结构已经覆盖基础字段，但后续可以进一步升级为层次化语义目标。比如把“松弛一点”抽象为低疲劳目标，把“吃点好的”抽象为餐饮质量优先，把“不要太商业”抽象为本地特色和非商圈优先。

层次化意图可以分为：

- 硬约束：必须满足。
- 软目标：尽量满足。
- 风格偏好：影响排序权重。
- 解释标签：用于前端展示系统理解。

这样能减少关键词依赖，提高泛化能力。

### 7.2 BERT 与语义向量化

当前系统主要依赖结构化标签、规则词典、评论关键词和手工/半结构化评价信号。这种方式的优势是稳定、可解释，也适合早期工程落地。但本地生活场景中，用户表达非常口语化，同一个需求可能有很多说法。例如“松弛感”“慢慢逛”“不要太赶”都可能指向低疲劳路线；“烟火气”“地道”“本地人会去”都可能指向本地特色；“吃点好的”“高级一点”“有品质”都可能指向更高质量或更高预算容忍的餐饮体验。

后续可以引入 BERT、Sentence-BERT、SimCSE 或中文 embedding 模型，把用户输入、POI 文本、UGC 评论和场景标签映射到统一语义空间。这样系统不只依赖关键词是否直接命中，而是可以计算语义相似度。

可以建立四类向量表示：

- 用户意图向量：由用户 query、解析后的偏好和上下文组成，表达本轮需求的整体语义。
- POI 向量：融合 POI 名称、类别、描述、标签、商圈和适用人群。
- UGC 向量：由评论关键词、正负面评论和评论信号组成，表达真实体验语义。
- 路线向量：由路线中的 POI 类型、顺序、节奏、转场和解释文本组成，表达整条路线风格。

在召回阶段，可以使用向量相似度补充候选。例如用户说“想找点本地人会去的地方”，即使 POI 标签中没有完全相同的词，也可以通过“老字号”“居民区”“地道”“烟火气”等评论语义召回相关地点。

在排序阶段，可以将语义相似度作为一个新的排序因子，与当前可解释规则分融合。这样做的好处是：规则分负责硬约束和风险控制，向量分负责长尾语义泛化。系统既不会变成纯黑盒，也能更好处理自然语言中不规则、非标准、带情绪和场景感的表达。

更进一步，可以使用向量聚类分析高频用户需求，沉淀新的语义目标。例如从用户输入和修改反馈中聚类出“低疲劳路线”“高质量餐饮”“城市漫步”“雨天室内”“本地生活感”等目标，再反向完善标签体系和评测用例。这会让系统从被动补词典，发展为持续发现新场景。

### 7.3 多路召回

后续可以将召回升级为多路召回：

- 类别召回保证基础需求。
- 地理召回保证路线可走。
- 向量召回处理长尾语义。
- 评论信号召回处理“拍照”“安静”“本地特色”等体验需求。
- 个性化召回处理用户稳定偏好。
- 探索召回增加新鲜感。

多路召回后可以使用融合排序，将不同召回来源合并成统一候选池，并保留召回原因。

### 7.4 学习排序

现有排序规则可解释，后续可以加入 Learning-to-Rank 作为增强因子。用户选择、收藏、删除、修改和分享都可以形成训练信号。

排序模型可以输入：

- 用户意图特征。
- POI 属性特征。
- 评论信号特征。
- 地理和转场特征。
- 当前上下文特征。
- 历史反馈特征。

模型输出作为数据驱动分，与当前规则分融合。这样既保留可解释性，也能从用户行为中学习。

### 7.5 带约束组合优化

路线规划可以进一步形式化为 Orienteering Problem 或 Prize-Collecting TSP 的变体。每个 POI 有收益，站点之间有成本，路线受时间、预算、营业时间、类别覆盖和疲劳度约束。

后续可以在 Beam Search 中加入：

- 上界估计。
- 候选剪枝。
- 局部搜索。
- 2-opt 或站点交换。
- 动态收益。
- 多样性约束。

这样可以提升路线整体最优性。

### 7.6 多目标 Pareto 优化

真实路线没有唯一最优。后续可以同时优化体验收益、转场成本、预算成本、疲劳成本、风险成本和多样性收益，并生成 Pareto 候选方案。

系统可以给用户展示：

- 综合推荐。
- 紧凑少走。
- 低预算。
- 体验丰富。
- 低风险。

每个方案都说明取舍，帮助用户做决策。

### 7.7 时空动态收益

后续可以把 POI 收益设计为时间相关函数。例如：

- 夜景点晚上收益更高。
- 餐饮点饭点收益更高。
- 咖啡点下午收益更高。
- 展览点闭馆前收益下降。
- 户外点雨天收益下降。

路线规划时根据到达时间动态计算收益，使路线顺序更符合真实出行。

### 7.8 不确定性和稳健规划

排队、拥挤、交通和天气都存在不确定性。后续可以把这些因素从单点估计扩展为风险分布。例如转场时间分为乐观、正常、保守三档；排队风险用概率估计；天气影响按室内外和雨天适配度计算。

稳健路线规划不只追求期望分最高，而是追求在多数情况下都稳定可执行。对于亲子、轻松、少排队等场景，这类稳健性非常重要。

### 7.9 路线修改最小编辑

用户修改路线时，通常希望保留原路线中合理的部分。后续可以将修改建模为最小编辑问题，在满足新约束的前提下，尽量减少删除、替换和重排。

编辑成本可以包括：

- 删除站点成本。
- 替换站点成本。
- 顺序调整成本。
- 新增转场成本。
- 类别覆盖损失成本。
- 违反新约束惩罚。

这样用户说“只把贵的换掉”“保留前两站”“最后改成夜景”时，系统能做更精细的局部修改。

### 7.10 Route Critic 闭环

后续可以增加独立 Route Critic，对生成路线进行二次评审。Critic 输出结构化评分，包括：

- 硬约束满足率。
- 偏好覆盖率。
- 避让项满足率。
- 路线连贯性。
- 阶段顺序满足率。
- 修改生效率。
- 解释一致性。

当评审发现问题时，系统可以触发重排、提高某类约束权重、重新召回或返回澄清问题。这样路线生成从一次性输出升级为生成、评审、修正的闭环。

### 7.11 反馈学习

用户行为可以反哺算法。可用反馈包括：

- 用户选择了哪个方案。
- 用户收藏或分享了哪条路线。
- 用户删除或替换了哪些站点。
- 用户反复要求更近、更便宜、更轻松、少排队。
- 用户是否实际完成路线。

这些反馈可以用于更新用户画像、调整策略权重、修正 POI 标签和训练排序模型。

### 7.12 评测指标体系

后续评测可以拆成四层。

意图解析指标：

- 城市识别准确率。
- 预算解析准确率。
- 时间解析准确率。
- 类别识别 F1。
- 偏好识别 F1。
- 避让项识别 F1。
- 必去点命中率。
- 阶段顺序识别准确率。

POI 排序指标：

- Top-K 类别命中率。
- Top-K 偏好命中率。
- 高风险 POI 降权率。
- 预算适配率。
- 推荐理由一致性。

路线规划指标：

- 类别覆盖率。
- 必去点覆盖率。
- 预算超限率。
- 时间窗口满足率。
- 总转场占比。
- 片区聚合度。
- 路线多样性。
- 营业时间适配率。

路线修改指标：

- 修改生效率。
- 原路线保留率。
- 不合规站点替换率。
- 修改后预算、距离、排队风险变化幅度。

解释指标：

- 解释与 POI 属性一致性。
- 解释与用户意图一致性。
- 风险提示覆盖率。
- 修改 diff 解释完整度。

通过这些指标，后续每一次算法改动都可以量化验证。

## 8. 产品与工程优化展望

### 8.1 数据扩展

后续可以扩展更多城市和 POI 类型，并建立 POI 数据更新流程。数据可以来自外部地图平台、人工校验和用户反馈。重点不是只增加数量，而是增加语义厚度，例如评论信号、适用场景、风险标签和最佳访问时段。

### 8.2 地图增强

后续可以更深接入真实路网，把天地图路线结果用于规划阶段，而不仅是预览阶段。同时可以加入实时交通、天气、人流和开放状态，提升路线可执行性。

### 8.3 个性化增强

当前画像是会话级轻量版本，后续可以扩展为账号级长期画像，并加入时间衰减、显式反馈和隐式行为学习。画像仍应保持软偏置原则，避免覆盖用户当前明确表达。

### 8.4 前端体验增强

前端可以继续增强：

- 路线对比视图。
- 手动锁定、删除、替换站点。
- 修改前后差异展示。
- 分享卡片。
- 演示模式。
- 更清晰的地图转场展示。
- 更自然的异常状态引导。

## 9. 总结

MeituanAgent 的核心价值在于，它把自然语言理解、POI 推荐、路线组合、结果解释、方案切换、增量修改和轻量记忆整合成了一个可运行的本地生活路线规划系统。

项目的技术特点包括：

- 用 LLM-first 解析降低自然语言输入门槛。
- 用本地 schema 和规则归一化保证结果可控。
- 用多因子排序保证 POI 推荐可解释。
- 用 Beam Search 和路线评分生成可执行路线。
- 用多方案切换表达不同路线策略。
- 用修改接口支持真实多轮决策。
- 用上下文和画像提供个性化软偏置。
- 用地图服务和本地兜底保证演示稳定性。

从比赛角度看，项目不是单纯展示一个聊天机器人，而是展示一个完整的智能路线规划原型：它能理解用户需求，能做结构化决策，能解释推荐理由，能响应用户修改，并且具备继续扩展为产品级系统的工程基础。
