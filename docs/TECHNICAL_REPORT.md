# MeituanAgent 技术报告

## 1. 赛题理解

这道题真正要解决的不是“推荐几个地点”，而是“帮用户把一天或半天的本地出行决策做完”。

用户在出门前经常会有一组混合需求：想吃得好一点，但不想排队；想多逛几个地方，但不想太累；时间有限，还要顾及预算、距离、天气、同行人和个人偏好。传统搜索能找到地点，地图能算两点之间的路，但中间那一步“把多个地点组合成一条适合我的路线”仍然主要靠用户自己完成。

因此，我们把项目目标定义为：用户只需要自然表达出行想法，系统自动理解意图，结合 POI 数据、内容评价信号和用户偏好，生成一条可直接执行、可解释、可继续调整的本地路线。

这个目标和官方赛题中的几个关键词是一致的：

- 多个 POI 串联成完整路线，而不是单点推荐。
- 结合 POI 数据、UGC 智慧和用户偏好，而不是只看距离。
- 支持时间、距离、预算、排队等多条件约束。
- 生成个性化方案，并允许用户继续动态调整。

## 2. 项目当前形态

MeituanAgent 当前是一个可运行的 Flutter + FastAPI 原型。前端提供自然语言输入、城市选择、偏好标签、路线结果工作台、方案切换、地图预览和路线修改入口；后端负责意图解析、POI 召回、POI 排序、路线组合、解释生成、上下文记录和地图预览。

项目目前支持广州和上海两个城市，本地 POI 数据包含 125 个地点。每个 POI 不只是一个名称和坐标，还包含类别、片区、价格、评分、建议停留时间、营业时间、室内外属性、排队等级、适用人群、评论关键词、正负面评论和结构化评价信号。

这些字段让系统可以处理更接近真实出行的问题。例如“适合拍照”“本地特色”“排队风险低”“雨天更稳”“适合朋友/亲子/约会”等，不再只是展示标签，而是会进入召回、排序和路线规划过程。

## 3. 用户流程

用户的使用路径比较直接：

1. 在首页选择城市，输入一句自然语言需求。
2. 系统解析出城市、时间、预算、偏好、避让项、交通方式和必去点。
3. 如果需求太泛，系统先问一个关键澄清问题。
4. 后端根据意图召回候选 POI，并结合评价信号做排序。
5. 路线规划器把候选点组合成多站路线。
6. 前端展示路线摘要、站点时间线、推荐理由、风险提示、地图预览和多种方案。
7. 用户可以继续说“太贵了”“不要排队”“更轻松一点”“换成室内点”，系统基于当前路线重新调整。

这个流程覆盖了赛题要求的端到端链路：输入目标、结合 POI 和评价数据、自动生成多维路线方案、支持按时空和偏好约束动态调整。

## 4. 功能设计

### 4.1 自然语言路线生成

用户不需要填写复杂表单，可以直接说出需求。系统会将自然语言转成结构化意图，包括：

- 城市和起点。
- 开始时间和结束时间。
- 预算。
- 需要的 POI 类型。
- 偏好，例如美食、拍照、夜景、文艺、本地特色、亲子、朋友、安静、室内、citywalk。
- 避让项，例如不想排队、别太远、避开拥挤、不吃辣。
- 交通方式，例如步行、地铁、打车或混合。
- 必须包含的地标或区域。

正式路线生成采用 LLM-first 的解析方式，同时用本地词典和 schema 做收口。我们没有让大模型直接输出最终路线，而是让它负责理解自然语言，再把结果交给后端规划链路处理。这样既能利用大模型的表达理解能力，又能避免路线结果完全变成不可控文本。

### 4.2 多 POI 路线生成

系统输出的是完整路线，而不是 POI 列表。每条路线包含：

- 多个站点。
- 到达和离开时间。
- 建议停留时长。
- 站点之间的转场时间和距离。
- 每个站点的推荐理由。
- 总预算、总时长、总距离和站点数。

官方要求路线至少支持 3 个 POI 串联，并覆盖餐饮和娱乐/文化类型。当前 POI 类型覆盖餐饮、咖啡、展览、博物馆、夜景、街区、公园、购物和景点等，可以支撑包含餐饮、文化、娱乐和休闲的多站路线。

### 4.3 多条件约束

路线规划时，系统会同时考虑多种约束：

- 时间：根据用户时间窗口控制路线长短。
- 距离：优先选择片区更集中的站点，减少跨区域跳跃。
- 预算：根据 POI 人均价格控制总花费。
- 排队：降低高排队风险 POI 的优先级。
- 拥挤：对拥挤风险较高的点做惩罚。
- 室内外：雨天或室内偏好会影响候选选择。
- 顺序：支持“先吃饭”“饭后看夜景”“最后收尾”等表达。

很多用户需求本身是冲突的。比如“想吃好但不想排队”，不能简单只选最高分餐厅，也不能只选最冷门的店。我们的做法是把体验收益和风险惩罚放进同一个排序和路线评分过程，尽量找到更稳的折中方案。

### 4.4 多方案与个性化

路线结果不是一个唯一答案。系统会给出不同策略：

- 推荐方案：综合平衡体验、距离、预算和时间。
- 偏好优先版：更看重用户兴趣和 POI 评价信号。
- 紧凑少走版：更看重少转场、少绕路和低疲劳。

这样做的原因是，本地路线规划很少存在绝对最优解。用户常常是在几个可行方案之间做选择：想更省时间，还是想体验更丰富；想少走路，还是想多看几个点。多方案可以把这种取舍显性化。

个性化方面，系统同时考虑当前输入和轻量历史偏好。当前输入永远优先；历史偏好只在用户没有明确说明时作为软偏置。例如用户多次选择慢节奏、少排队或室内路线，后续系统可以轻微参考这些信号，但不会覆盖本轮明确表达。

### 4.5 路线修改

用户拿到路线后，往往不是立刻接受，而是会继续调整。我们把修改作为核心功能，而不是附加功能。

用户可以直接说：

- “太贵了”
- “不要排队”
- “更轻松一点”
- “再紧凑一点”
- “多一点拍照点”
- “换成室内点”

后端会继承当前路线中的城市、类别、偏好和已选站点，再叠加本轮修改要求。这样系统是在“改这条路线”，而不是每次重新生成一条陌生路线。

## 5. 算法设计

### 5.1 意图解析

意图解析是路线规划的入口。系统先用 LLM 提取结构化意图，再用本地规则做补充和校验。最终结果包括城市、时间、预算、类别、偏好、避让项、交通方式、必去点和未归类线索。

保留未归类线索是一个重要设计。比如用户说“vibe 感”“松弛一点”“不太商业”，有些表达不一定能立即稳定映射到现有标签，但我们会把它们保留下来，后续可以用于扩展词典、UGC 信号和评测样例。

### 5.2 POI 召回

召回阶段负责从本地 POI 数据中找到候选点。系统会按城市过滤，再结合类别、偏好、必去点、起点、评论关键词和评价信号进行召回。

例如：

- 用户想“雨天室内”，室内和雨天适配信号更重要。
- 用户想“拍照出片”，拍照分和相关评论关键词更重要。
- 用户想“本地特色”，本地标签、老字号、烟火气等信号更重要。
- 用户说“不要排队”，高排队等级的 POI 会被降低优先级。

召回阶段并不追求最终排序，而是保证候选池足够相关、足够丰富，后续排序和路线组合才有空间。

### 5.3 多因子排序

每个候选 POI 都会计算多个分项：

- 偏好匹配。
- 评价/语义信号匹配。
- 类别匹配。
- 评分质量。
- 预算适配。
- 时间适配。
- 排队惩罚。
- 拥挤惩罚。
- 价格惩罚。
- 修改惩罚。

最终排序不是黑盒分数，而是带有分项解释。系统可以说明为什么选择这个 POI，也可以说明它有什么风险。例如“符合餐饮需求但高峰可能排队”“适合夜景收尾”“成本较低，预算压力小”。

这种可解释性很适合本赛题，因为路线是否可用不只看结果，还要看系统是否真的理解并处理了用户约束。

### 5.4 路线组合

路线规划不是简单取排名最高的几个 POI。高分 POI 可能分散在不同区域，直接串起来会很绕；也可能类别重复，导致体验单一。

因此，系统在路线层面做组合搜索。当前实现使用 Beam Search 与启发式补全：先保证必去点和必要类别，再在候选 POI 中扩展路线，并用时间、预算、距离、片区聚合和路线质量进行评分。

路线评分会考虑：

- 总游览时间是否适配用户时间窗口。
- 交通时间占比是否过高。
- 选中 POI 的平均质量。
- 类别覆盖是否完整。
- 夜景和餐饮等时段顺序是否合理。
- 站点是否集中在相近片区。
- 总预算是否可接受。
- 营业时间是否适配。

这样生成的路线更接近“能直接用”的路线，而不是简单地点拼接。

## 6. 项目创新点

### 6.1 从搜索列表到路线决策

很多产品可以告诉用户“有哪些地方值得去”，但仍需要用户自己判断顺序、距离、预算和时间。我们的系统直接生成路线，并且把站点顺序、停留时间、转场信息和风险提示一起给出，减少用户做攻略和反复筛选的成本。

### 6.2 LLM 与规划算法分工明确

我们没有把所有事情都交给大模型。LLM 负责理解自然语言，后端算法负责路线决策。这个分工让系统既有自然语言交互能力，又保留了路线规划的稳定性和可解释性。

### 6.3 UGC 信号进入路线决策

POI 数据里包含评论关键词、正负面评价和体验信号。系统会把这些内容信号转成排序因素，让“拍照好看”“少排队”“适合雨天”“本地特色”等真实体验进入路线生成，而不是只看类别和距离。

### 6.4 支持多轮修改

路线规划不是一次性答案。用户修改路线时，系统会基于当前路线做增量调整，并保留修改前后的变化。这一点让项目更像一个可以协作的出行助手，而不是一个静态推荐器。

### 6.5 具备继续发展的空间

当前系统已经形成了清晰的链路：意图解析、POI 召回、排序、路线组合、解释、修改和上下文。这个链路天然可以继续扩展，而不是一次性 demo。

后续可以扩展更多城市和 POI，也可以加入真实地图、人流、天气、营业状态、更多 UGC 信号和用户反馈学习。算法层也可以继续升级为多路召回、学习排序、多目标优化和 Route Critic。

## 7. 应用效果

从用户角度看，系统解决的是三个实际问题。

第一，减少决策成本。用户不需要反复搜索和手动拼接路线，只要表达目标，系统给出可执行方案。

第二，减少踩雷风险。系统会考虑排队、拥挤、预算、雨天、营业时间和转场距离，并把风险提示展示出来。

第三，支持继续调整。用户可以在看到路线后继续改，而不是重新开始。

从比赛展示角度看，系统具备完整演示闭环：输入自然语言、生成路线、多方案切换、查看解释、地图预览、继续修改。

当前离线评测集包含 25 个用例，覆盖意图解析和路线修改。本地运行结果为 25/25 通过。该评测主要验证本地规则解析和后续规划链路的稳定性，也为后续扩展词典、权重和路线策略提供回归基础。

## 8. 对赛事关注点的回应

官方关注完整性、创新性和应用效果。我们的对应关系如下。

完整性方面，项目已经覆盖从用户输入到路线生成、方案展示、解释、修改和上下文记录的完整流程。路线支持多个 POI 串联，类型覆盖餐饮、咖啡、展览、博物馆、夜景、街区、公园、购物和景点等。

创新性方面，项目重点不在于单纯调用大模型，而在于把 LLM 理解、POI/UGC 信号、可解释排序和路线组合规划结合起来。用户还能通过自然语言继续修改已有路线，形成反馈闭环。

应用效果方面，前端不是纯文本输出，而是路线工作台。用户能看到路线摘要、站点时间线、方案差异、推荐理由、风险提示和地图预览。即使地图 key 未配置，系统也能用本地经纬度估算兜底，保证演示稳定。

## 9. 发展方向

这个项目比较有发展性的地方在于，它的核心链路可以自然扩展。

### 9.1 数据发展

当前 POI 数据已经能支持广州和上海的路线演示。后续可以扩展更多城市，增加更多 POI 类型，并把真实评价、排队、营业状态、适合人群和场景标签做得更细。数据越厚，路线越能接近真实本地生活体验。

### 9.2 算法发展

当前排序是可解释规则模型，路线组合使用 Beam Search。后续可以逐步加入：

- 语义向量表示：使用 BERT、Sentence-BERT 或中文 embedding 模型，将用户需求、POI 描述、评论关键词和场景标签映射到同一语义空间。
- 多路召回：类别召回、地理召回、语义召回、UGC 信号召回、个性化召回。
- 学习排序：利用用户选择、收藏、删除、修改行为调整排序。
- 多目标优化：生成省钱、少走路、体验丰富、低风险等 Pareto 方案。
- 局部修改算法：让“只换贵的”“保留前两站”“最后换夜景”等修改更精确。

语义向量化是后续比较重要的一步。当前系统主要依赖结构化标签、词典和评论信号，优点是可解释、可控，但对一些长尾表达仍需要不断补词典。引入 BERT 类模型后，可以把“松弛感”“不太商业”“适合慢慢逛”“有烟火气”“吃点好的”这类表达转成向量，与 POI 的描述、UGC 评论和场景标签做相似度匹配。这样系统不仅能识别明确关键词，也能识别语义接近但措辞不同的需求。

后续可以把召回设计成“规则召回 + 向量召回”的混合结构。规则召回负责保证城市、预算、类别、必去点等硬约束不丢；向量召回负责补充那些语义相似但没有直接关键词命中的 POI。排序阶段再把语义相似度作为一个新因子，与现有的预算、排队、距离、评分、类别覆盖等因素融合。这样既保留当前系统的可解释性，又能提升对自然语言复杂表达的泛化能力。

更进一步，可以为用户意图、POI、UGC 和路线方案分别建立表示：

- 用户意图向量：表达本轮需求的整体语义。
- POI 向量：融合名称、类别、描述、标签和评论关键词。
- UGC 向量：从正负面评论中提取体验语义，例如排队、服务、拍照、氛围、性价比。
- 路线向量：表示一条路线的整体风格，例如轻松、紧凑、文化、本地、美食、夜景。

有了这些表示后，系统可以从“关键词命中”逐步发展到“语义匹配”。例如用户说“想找点本地人会去的地方”，即使 POI 标签里没有完全一样的词，也可以通过评论中的“地道”“老字号”“居民区”“烟火气”等语义信号召回相关地点。这个方向和赛题强调的 POI 数据、UGC 智慧、用户偏好的结合也更一致。

### 9.3 Route Critic

后续可以增加一个独立的路线评审模块，对生成路线做二次检查。它可以判断路线是否满足硬约束、偏好是否覆盖、修改是否生效、解释是否一致。如果评审不通过，系统可以自动重排或提出澄清。

这样系统就会从“一次生成”变成“生成 - 评审 - 修正”的闭环。

### 9.4 真实世界约束

后续可以把真实地图路网、天气、人流、营业时间和排队风险更深地接入路线规划。这样系统不仅能回答“去哪”，还能更好地回答“什么时候去、怎么走、这条路线稳不稳”。

### 9.5 产品发展

前端可以继续加入路线对比、站点锁定、手动替换、修改前后 diff、分享卡片和演示模式。这样路线结果会从“可以看”进一步变成“可以协作调整、可以直接出发”。

## 10. 总结

MeituanAgent 围绕“AI 本地路线智能规划”构建了一个完整原型。它用自然语言降低输入成本，用 POI 和 UGC 信号提升路线质量，用可解释排序和路线组合处理多条件约束，用路线工作台和动态修改完成用户闭环。

这个项目当前已经能够完成比赛要求的核心流程，也保留了清晰的发展方向。后续随着 POI 数据、UGC 信号、地图信息和用户反馈的增强，它可以从黑客松原型继续成长为更完整的本地生活出行决策助手。
